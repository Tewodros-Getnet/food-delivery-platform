# Requirements: Admin User Management Privileges

## Introduction

The admin dashboard currently allows listing, searching, filtering by role, and toggling suspend/reactivate on user accounts. This feature extends the admin's user management capabilities with nine additional operations: account deletion, role change, password reset by email, a detailed user profile side panel, user impersonation via short-lived JWT, CSV export of filtered lists, push notification delivery, status filtering, and sortable column headers. Together these give admins full lifecycle control over user accounts while enforcing role-based guardrails that protect admin accounts from modification by peers.

---

## Requirements

### 1. Delete User Account

**1.1** WHEN an admin clicks "Delete" on a non-admin user and confirms the dialog, THEN the system SHALL permanently delete the user row, revoke all active sessions (refresh tokens), and return a 200 success response.

**1.2** WHEN a user account is deleted, THEN the system SHALL preserve all order history records associated with that user (orders rows are kept; only the user row is removed).

**1.3** WHEN an admin attempts to delete a user whose role is `admin`, THEN the system SHALL reject the request with HTTP 403 and an appropriate error message, without deleting the account.

**1.4** WHEN an admin clicks "Delete" on a user, THEN the system SHALL display a confirmation dialog naming the user before the deletion is executed.

**1.5** WHEN the deletion request fails on the backend, THEN the system SHALL display an error message in the UI and leave the user list unchanged.

---

### 2. Change User Role

**2.1** WHEN an admin selects a new role (customer, restaurant, or rider) for a non-admin user and confirms, THEN the system SHALL update the user's role in the database and return a 200 success response.

**2.2** WHEN an admin attempts to change a user's role to `admin`, THEN the system SHALL reject the request with HTTP 422 and an error message stating that the admin role cannot be assigned.

**2.3** WHEN an admin attempts to change the role of a user who currently has the `admin` role, THEN the system SHALL reject the request with HTTP 403.

**2.4** WHEN a role change succeeds, THEN the system SHALL revoke all of the user's active refresh tokens so their next login reflects the new role.

**2.5** WHEN a role change request fails, THEN the system SHALL display an error notification in the admin UI and leave the role unchanged.

---

### 3. Reset Password (Send Password Reset Link)

**3.1** WHEN an admin triggers "Send Password Reset" for a user, THEN the system SHALL generate a cryptographically secure, single-use reset token, store its hash with a 1-hour expiry, and send a password reset email to the user's address via SendGrid.

**3.2** WHEN a password reset token is generated by an admin, THEN the system SHALL invalidate any previously issued, unused password reset tokens for that user.

**3.3** WHEN the user clicks the reset link and submits a new password, THEN the system SHALL validate the token is unused and unexpired, update the password hash, mark the token as used, and revoke all active refresh tokens for that user.

**3.4** WHEN a reset token has expired or has already been used, THEN the system SHALL reject the reset attempt with HTTP 400 and a clear error message.

**3.5** WHEN the admin triggers a reset for a user, THEN the system SHALL return HTTP 200 immediately after queuing the email, without waiting for email delivery confirmation.

---

### 4. View User Details Side Panel

**4.1** WHEN an admin clicks a user row in the table, THEN the system SHALL open a slide-over side panel containing: full profile fields (display name, email, phone, profile photo), account status, email verification status, role, registration date, and last seen date (derived from the user's most recent refresh token).

**4.2** WHEN the side panel is open, THEN the system SHALL display the user's 5 most recent orders including order ID, status, total amount, and date.

**4.3** WHEN the side panel is open, THEN the system SHALL display an account status history log showing the timestamps and reasons for any suspend/reactivate actions applied to the account.

**4.4** WHEN a user has no orders, THEN the system SHALL display an empty state message within the panel rather than an error.

**4.5** WHEN a user has no profile photo, THEN the system SHALL display a fallback avatar (initial letter of display name or email) in the side panel.

**4.6** WHEN the admin closes the side panel, THEN the system SHALL dismiss the panel without navigating away from the users list.

---

### 5. Impersonate User

**5.1** WHEN an admin clicks "Impersonate" on a non-admin user, THEN the system SHALL generate a short-lived JWT (15-minute expiry) scoped to that user's identity and return it in the response.

**5.2** WHEN the impersonation token is returned, THEN the admin UI SHALL copy the token to the clipboard and display a success toast notification.

**5.3** WHEN an admin attempts to impersonate a user whose role is `admin`, THEN the system SHALL reject the request with HTTP 403.

**5.4** WHEN generating an impersonation token, THEN the system SHALL include an `impersonatedBy` claim (the acting admin's user ID) in the JWT payload for audit purposes.

**5.5** WHEN the impersonation token expires after 15 minutes, THEN the system SHALL not allow it to be refreshed; no refresh token is issued for impersonation sessions.

---

### 6. Export Users to CSV

**6.1** WHEN an admin clicks "Export CSV", THEN the system SHALL generate and download a CSV file containing all users that match the currently active search, role filter, and status filter (not limited to the current page).

**6.2** WHEN generating the CSV, THEN the system SHALL include the following columns: `id`, `email`, `role`, `display_name`, `phone`, `status`, `email_verified`, `created_at`, `order_count`.

**6.3** WHEN no users match the current filters, THEN the system SHALL still produce a valid CSV file containing only the header row.

**6.4** WHEN the export is triggered, THEN the browser SHALL prompt a file download with a descriptive filename (e.g., `users-export-YYYY-MM-DD.csv`).

**6.5** WHEN the export request fails, THEN the system SHALL display an error notification to the admin.

---

### 7. Send Push Notification to User

**7.1** WHEN an admin opens the notification form for a user, fills in a title and message, and submits, THEN the system SHALL deliver a push notification to all FCM tokens registered for that user.

**7.2** WHEN the notification is sent successfully (at least one token delivery succeeds), THEN the system SHALL return HTTP 200 and display a success toast in the admin UI.

**7.3** WHEN the target user has no registered FCM tokens, THEN the system SHALL return HTTP 200 with a message indicating no device tokens were found, without throwing an error.

**7.4** WHEN the notification title or body is empty, THEN the system SHALL reject the request with HTTP 422 before attempting FCM delivery.

**7.5** WHEN FCM delivery fails for all tokens, THEN the system SHALL log the failure but return HTTP 200 to the admin (consistent with existing FCM service behavior where push failure does not block operations).

---

### 8. Filter by Status

**8.1** WHEN an admin selects a status from the status filter dropdown (All / Active / Suspended), THEN the system SHALL re-query the user list filtered to that status and reset to page 1.

**8.2** WHEN the status filter is combined with the existing role filter and/or search query, THEN the system SHALL apply all filters conjunctively (AND logic).

**8.3** WHEN the status filter is set to "All", THEN the system SHALL return users of any status with no status constraint applied.

**8.4** WHEN the backend `/admin/users` endpoint receives a `status` query parameter, THEN the system SHALL add a `WHERE status = $n` clause to the database query.

---

### 9. Sort Columns

**9.1** WHEN an admin clicks a sortable column header (Email, Role, Activity, Status, Joined), THEN the system SHALL re-fetch the user list sorted by that column in ascending order.

**9.2** WHEN an admin clicks the same column header a second time, THEN the system SHALL toggle the sort direction to descending and re-fetch.

**9.3** WHEN a sort is active, THEN the system SHALL display an arrow indicator (↑ ascending / ↓ descending) next to the active column header.

**9.4** WHEN any filter or search is changed while a sort is active, THEN the system SHALL retain the active sort column and direction in the new query.

**9.5** WHEN the backend `/admin/users` endpoint receives `sortBy` and `sortDir` query parameters, THEN the system SHALL apply an `ORDER BY` clause using a server-side whitelist of allowed column names to prevent SQL injection.
